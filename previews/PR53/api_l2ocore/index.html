L2OCore API

L2OCore lives in lib/L2OCore of this repository. All of its exported names are re-exported by LearningToOptimize.

L2OCore.L2OCore — Module
L2OCore

Lightweight interfaces shared by every Learning-to-Optimize (L2O) method in the LearningToOptimize ecosystem.

L2OCore defines what an L2O method is (a type in a small hierarchy), which problems it accepts (supports), how its predictions are evaluated (evaluate) and the method-dispatched pipeline

ParametricProblem ─ decompose ─ generate_data ─ (train proxy) ─ complete ─ evaluate

with sane fallbacks for each method family. It depends only on JuMP, MathOptInterface and standard libraries, so method packages can depend on it without pulling in a machine-learning framework.

Conventions:

  • Batch-first: the batch is always the last dimension. Parameters are num_parameters × B, primal predictions num_decision_variables × B, dual predictions num_duals × B.
  • Element-type generic: evaluators are parametrized by the element type.
  • Minimal scalar indexing in vectorized evaluation code so arrays can be moved to accelerators by a future kernels extension.

Methods and proxies

L2OCore.AbstractL2OMethod — Type
AbstractL2OMethod

Supertype of every Learning-to-Optimize method.

A method is a (usually small, immutable) struct holding its hyper-parameters. Concrete methods subtype one of the three families AbstractPrimalMethod, AbstractDualMethod or AbstractPrimalDualMethod; the family selects the fallback behavior of decompose, generate_data, loss and complete.

To add a method, a package defines

struct MyMethod <: L2OCore.AbstractPrimalMethod
    ρ::Float64
end
L2OCore.supports(::MyMethod, ::L2OCore.LinearConic) = true

and overrides only the pipeline steps that differ from the family fallback.

source
L2OCore.AbstractPrimalMethod — Type
AbstractPrimalMethod <: AbstractL2OMethod

Methods whose proxy predicts (a subset of) the primal decision variables, e.g. penalty methods, DC3, LDF.

source
L2OCore.AbstractDualMethod — Type
AbstractDualMethod <: AbstractL2OMethod

Methods whose proxy predicts (a subset of) the dual variables, e.g. Dual Lagrangian Learning (DLL). A dual feasible prediction gives a valid bound on the optimal value through dual_bound.

source
L2OCore.AbstractPrimalDualMethod — Type
AbstractPrimalDualMethod <: AbstractL2OMethod

Methods that predict both primal and dual variables, e.g. primal-dual learning with an augmented Lagrangian (ALM/PDL).

source
L2OCore.AbstractMethodWrapper — Type
AbstractMethodWrapper <: AbstractL2OMethod

A method that wraps another method and changes only part of its behavior — the hook for method-agnostic add-ons such as derivative (Sobolev) supervision or extra regularizers. A wrapper must implement

  • L2OCore.inner_method(w) → the wrapped method;
  • L2OCore.extra_loss(w, pipe, inputs, output; targets, proxy, kwargs...) → the additional loss term (a scalar).

Leave the pipe, inputs and output arguments untyped (or typed no more narrowly than the fallbacks) to avoid method ambiguities. Everything else (family, supports, decompose, generate_data, complete) is forwarded to the inner method, and loss is loss(inner) + extra_loss(wrapper). A wrapper may override any of them, e.g. generate_data to attach derivative labels with with_derivatives.

L2OCore.SupervisedMSE — Type
SupervisedMSE()

Plain value supervision: the proxy predicts all decision variables and is trained on solver labels with the mean squared error

\[\mathcal{L}(θ) = \frac{1}{N n} \sum_{i=1}^{N} \big\| \hat g_θ(p_i) - x^\star(p_i) \big\|_2^2 ,\]

the empirical-risk-minimization baseline of the optimization-proxy literature (the value term of supervised Sobolev training). It is the primal family fallback made concrete: generate_data solves every sampled instance for primal labels, complete is the identity and loss is the supervised MSE against targets.

It needs a solver that returns (locally) optimal primal solutions for the sampled parameters and accepts any problem class, since labels are only data. A regression proxy is in general infeasible; measure its violations with evaluate.

source
L2OCore.AbstractProxyModel — Type
AbstractProxyModel

Optional supertype for proxy models (the learned map from parameters to raw outputs).

L2OCore is framework-agnostic: any callable f(inputs::AbstractMatrix) returning an output_dimension × B array can be used as a proxy (a Flux.Chain, a closure over a Lux model and its state, a plain function). Subtyping AbstractProxyModel is only needed to attach extra behavior, for example a custom predict_batch or trainable-parameter handling.

source

predict_batch(proxy, inputs::AbstractMatrix)

Problems and classes

L2OCore.AbstractProblemClass — Type
AbstractProblemClass

Trait describing the mathematical class of a parametric problem for fixed parameters. Methods declare which classes they accept with supports.

The built-in classes are ordered from most to least structured: LinearConic ⊂ ConvexQuadratic (as objective classes), SmoothNonlinear and MixedInteger. Packages may add classes by subtyping AbstractProblemClass (or AbstractConvexClass) and passing the class explicitly to ParametricProblem.

source
L2OCore.AbstractConvexClass — Type
AbstractConvexClass <: AbstractProblemClass

Problem classes for which every instance (for fixed parameters) is a convex optimization problem, so that weak and strong duality arguments (under a constraint qualification) apply.

source
L2OCore.LinearConic — Type
LinearConic()

Affine objective, affine constraint functions in (products of) closed convex cones: LPs, SOCPs, SDPs, exponential-cone programs, …

Parameters may appear affinely in the objective and in the constraint constants.

source
L2OCore.ConvexQuadratic — Type
ConvexQuadratic()

Convex quadratic objective (½xᵀQx + cᵀx with Q ⪰ 0 for minimization, Q ⪯ 0 for maximization) and affine conic constraints.

source
L2OCore.SmoothNonlinear — Type
SmoothNonlinear()

Continuous problems with nonlinear (or nonconvex quadratic) objective or constraints, e.g. AC optimal power flow. Only first-order stationarity is meaningful; weak duality still holds but certificates require extra work.

source
L2OCore.MixedInteger — Type
MixedInteger()

Problems with integrality restrictions (Integer, ZeroOne, semi-continuous or SOS constraints).

source
L2OCore.detect_problem_class — Function
detect_problem_class(model::JuMP.Model; atol = 1e-9) -> AbstractProblemClass

Inspect a JuMP model and return the most structured built-in class that describes it:

  1. any integrality/SOS/semi-continuous constraint → MixedInteger;
  2. any nonlinear expression, legacy @NL block or quadratic constraint with a product of two decision variables → SmoothNonlinear;
  3. quadratic objective with a product of decision variables → convexity is checked numerically (eigmin(sQ) ≥ -atol, s = ±1 for the sense): ConvexQuadratic if convex, SmoothNonlinear otherwise;
  4. otherwise LinearConic.

Products parameter × variable do not change the class (for fixed parameters they are affine in the decision variables).

source
L2OCore.AbstractParametricProblem — Type
AbstractParametricProblem

Supertype of parametric problems, independent of the modeling front end. ParametricProblem is the JuMP front end; other front ends (for example an ExaModels-based one) subtype this and implement problem_class, num_parameters, num_decision_variables, num_duals, objective_sign and default_evaluator (and solve_instances to support solver-labeled data).

source
L2OCore.ParametricProblem — Type
ParametricProblem(model::JuMP.Model; class = detect_problem_class(model))

A parametric optimization problem: a JuMP model in which the problem data that changes between instances are declared as parameters (@variable(model, p in MOI.Parameter(value))).

The wrapper fixes three layouts used throughout the ecosystem:

  • inputs: parameters, in creation order (num_parameters × B);
  • primal: decision_variables = all non-parameter variables in creation order (num_decision_variables × B);
  • dual: constraint_refs, including variable bounds but not parameter or integrality constraints; constraint i owns the rows dual_layout(problem)[i] (num_duals × B). Signs follow the MathOptInterface convention returned by JuMP.dual.

class is a trait (AbstractProblemClass) used by supports; pass it explicitly to override detection (e.g. to declare a convex QCQP or a custom class).

Fields are considered internal; use the accessor functions.

L2OCore.supports — Function

Evaluation

L2OCore.AbstractEvaluator — Type
AbstractEvaluator

Batch evaluation backend for a ParametricProblem. Evaluators turn batches of parameters P (num_parameters × B), primal points X (num_decision_variables × B) and dual points Y (num_duals × B) into objective values, constraint violations and dual bounds.

Built-in backends:

  • MatrixEvaluator: extracts A, Q, c, … once and evaluates with array operations (vectorized, differentiable by array AD, element-type generic). Used for LinearConic and ConvexQuadratic problems whose parameters enter affinely.
  • JuMPEvaluator: per-instance fallback through JuMP.value; works for any expression JuMP can evaluate (including nonlinear) but is not meant to be differentiated.

Extension point. Kernel packages (e.g. an ExaModels/BatchNLPKernels extension) add a backend by subtyping AbstractEvaluator and implementing

functionrequiredreturns
batch_objective(ev, X, P)yeslength-B vector
constraint_values(ev, X, P)yesnum_duals × B
row_violation(ev, X, P)yesnum_duals × B, ≥ 0
equality_rows(ev)yesBitVector of length num_duals
cone_violation(ev, X, P)if non-decomposable conesn_cones × B, ≥ 0
dual_bound(ev, Y, P)for dual methods(bound, infeasibility) vectors

and, optionally, a method of default_evaluator for the problems it should handle.

source
L2OCore.MatrixEvaluator — Type
MatrixEvaluator(problem::ParametricProblem; T = Float64)

Matrix-form evaluator for problems of the form (for each instance p)

\[\min_x \; \tfrac12 x^\top Q x + c^\top x + x^\top H p + c_p^\top p + \tfrac12 p^\top Q_{pp} p + c_0 \quad \text{s.t.} \quad A x + B p + b \in \mathcal{K}\]

where 𝒦 is the product of the constraint sets in dual_layout order (max is handled through the sense). Box-like sets become row bounds l ≤ Ax + Bp + b ≤ u; other cones are kept as blocks.

All batch operations are matrix products and broadcasts, so they are vectorized, allocation-light and differentiable with array AD (Zygote, Enzyme, …). cone_violation and the cone part of dual_bound evaluate MOI.Utilities.distance_to_set per column (differentiable with Zygote for the second-order cone; not GPU-friendly).

source
L2OCore.JuMPEvaluator — Type
JuMPEvaluator(problem::ParametricProblem)

Reference evaluator that loops over the batch and evaluates every expression with JuMP.value(var_value, expr). It supports anything JuMP can evaluate (affine, quadratic and GenericNonlinearExpr functions, any MOI set with MOI.Utilities.distance_to_set) and serves as the ground truth against which faster backends are tested. It is not meant for training loops.

dual_bound is not available for this backend.

source
L2OCore.default_evaluator — Function
default_evaluator(problem::ParametricProblem; T = Float64) -> AbstractEvaluator

MatrixEvaluator when the problem can be put in matrix form (affine constraints, at most quadratic objective, parameters entering affinely), otherwise JuMPEvaluator. The result is cached in the problem.

source
L2OCore.has_matrix_form — Function
has_matrix_form(problem::ParametricProblem) -> Bool

Whether MatrixEvaluator can represent problem: affine constraint functions (parameters may appear in the constants), at most quadratic objective, no legacy @NL block.

L2OCore.batch_objective — Function
batch_objective(ev::AbstractEvaluator, X, P) -> AbstractVector

source
L2OCore.constraint_values — Function
constraint_values(ev::AbstractEvaluator, X, P) -> AbstractMatrix

source
L2OCore.row_violation — Function
row_violation(ev::AbstractEvaluator, X, P) -> AbstractMatrix

Element-wise violation max(l - f, 0) + max(f - u, 0) of every row whose set is a box (EqualTo, GreaterThan, LessThan, Interval, Zeros, Nonnegatives, Nonpositives), and 0 for rows of non-decomposable cones (see cone_violation). Shape num_duals × B.

source
L2OCore.cone_violation — Function
cone_violation(ev::AbstractEvaluator, X, P) -> AbstractMatrix

Euclidean distance of each non-decomposable conic constraint (second-order, PSD, exponential, …) to its set, n_cones × B. The fallback returns a 0 × B matrix.

source
L2OCore.equality_rows — Function
equality_rows(ev::AbstractEvaluator) -> BitVector

Mask of rows (in dual_layout order) that are equality constraints.

source
L2OCore.bound_rows — Function
bound_rows(ev::AbstractEvaluator) -> BitVector

Mask of rows that are variable bounds (VariableRef-in-set constraints).

source
L2OCore.dual_bound — Function
dual_bound(ev::AbstractEvaluator, Y, P; atol = 1e-6) -> (bound, infeasibility)

Value of the Lagrangian dual function at each column of Y (signs as returned by JuMP.dual) and the dual infeasibility of that column.

By weak duality, whenever infeasibility[k] ≤ atol, bound[k] is a lower bound (upper bound for maximization) on the optimal value of instance k, up to infeasibility[k] * ‖x⋆‖₁ when the stationarity residual is nonzero (see the Theory page). Columns that are not dual feasible get bound = -Inf (+Inf for maximization).

Dual signs follow JuMP.dual (the MathOptInterface convention). For quadratic objectives sQ ⪰ 0 is required and verified; otherwise no bound is returned.

source
L2OCore.EvaluationReport — Type
EvaluationReport

Per-instance quality metrics returned by evaluate. Every field is a length-B vector or nothing when it does not apply.

  • objective: primal objective of the prediction;
  • max_violation: largest violation over all constraints;
  • max_equality_violation, max_inequality_violation;
  • dual_bound, dual_infeasibility: see dual_bound;
  • gap: |objective - dual_bound| / max(1, |objective|) when both a primal and a feasible dual prediction are available.
source
L2OCore.evaluate — Function
evaluate(pipe::L2OPipeline, inputs, prediction; atol = 1e-6)
evaluate(problem::ParametricProblem, inputs, prediction;
         evaluator = default_evaluator(problem), atol = 1e-6)

Quality metrics of a batch of completed predictions as an EvaluationReport: objective and violations of the primal part, dual bound and dual infeasibility of the dual part, and the gap when both exist.

L2OCore.L2ODataset — Type
L2ODataset

Columns-as-samples dataset (N samples):

  • inputs: num_parameters × N (always present);
  • primal: num_decision_variables × N or nothing;
  • dual: num_duals × N or nothing;
  • objective: length N or nothing;
  • status: termination status per sample or nothing (unsolved data, e.g. for self-supervised methods);
  • derivatives: an AbstractDerivativeLabels or nothing;
  • metadata: free-form Dict{String,Any} (problem id, sampler, solver, tolerances…), mirrored by the dataset-card conventions in the design docs.

Samples whose solve failed hold NaN labels; filter them with ds[findall(ok)] where ok comes from status.

L2OCore.JacobianLabels — Type
JacobianLabels(J)

L2OCore.PullbackLabels — Type
PullbackLabels(seeds, values)

Vector–Jacobian products: for each sample k, values[:, k] = J_kᵀ seeds[:, k] where J_k = ∂x*/∂p; seeds is num_decision_variables × N, values is num_parameters × N. Cheaper than full Jacobians and sufficient for pullback-based Sobolev losses.

source
L2OCore.PushforwardLabels — Type
PushforwardLabels(directions, values)

Jacobian–vector products: for each sample k, values[:, k] = J_k directions[:, k] where J_k = ∂x*/∂p; directions is num_parameters × N, values is num_decision_variables × N. The forward-mode counterpart of PullbackLabels: cheaper than full Jacobians when the number of parameters is large, and sufficient for directional Sobolev losses.

L2OCore.generate_data — Function
generate_data(::SobolevRegularized, pipe; sampler, n, rng = Random.default_rng(),
              optimizer = nothing, oracle = DiffOptSensitivities(optimizer),
              drop_failed = true, consistency_atol = 1e-4,
              consistency_rtol = 1e-4, max_label_error = Inf,
              fd_step = 1e-5, kwargs...)

Dataset of the wrapped method (same sampler, n, rng, optimizer, kwargs) with derivative labels of w.directions from oracle attached as ds.derivatives. Samples whose label solve failed are dropped when drop_failed; so are samples whose primal labels (if the wrapped method records them) differ from the oracle's solution by more than consistency_atol + consistency_rtol * ‖x‖_∞ in the max norm (a different local optimum would make value and derivative labels describe different solution branches). The number of dropped samples is stored in ds.metadata["sobolev_dropped"].

With a finite max_label_error, the labels are also verified against central finite differences of the solver map (label_errors with step = fd_step, 2d extra solves per sample) and samples whose relative error exceeds it are dropped: these are the degenerate samples (weakly active constraints, active-set changes within ± fd_step) where the solution map is not differentiable and the KKT sensitivities of eq. (1) of the paper are not its derivative. Their number is stored in ds.metadata["sobolev_degenerate"].

source
generate_data(pipe::L2OPipeline; sampler, n, rng = Random.default_rng(), kwargs...)
generate_data(method, pipe; sampler, n, rng, kwargs...)  # extension point

Build an L2ODataset for training pipe.method.

Family fallback: sample n parameter vectors from sampler and solve every instance with solve_instances (kwargs such as optimizer are forwarded), recording primal labels for primal methods, dual labels for dual methods and both for primal-dual methods. Methods override the second form, e.g. self-supervised methods that need only inputs, or DC3 storing only independent variables.

source
generate_data(::PenaltyMethod, pipe; sampler, n, rng, optimizer = nothing)

Penalty training is self-supervised: only parameters are sampled. When an optimizer is given, instances are also solved so that the dataset carries reference optima for evaluation (objective gaps, dual bounds).

source
L2OCore.complete — Function
complete(pipe::L2OPipeline, inputs, output) -> Prediction
complete(method, pipe, inputs, output)  # extension point

Turn the raw proxy output (output_dimension × B) into a Prediction in the method's own sense (projection, equality completion, dual completion, repair…). The FullSpaceDecomposition fallback only splits the output into primal and dual blocks.

Implementations should be written with array operations so they can be differentiated and run on accelerators when the loss needs them.

source
L2OCore.loss — Function
loss(pipe::L2OPipeline, inputs, output; targets = nothing) -> Real
loss(method, pipe, inputs, output; targets)  # extension point

Training loss of a batch of raw proxy outputs. Training loops should also pass proxy = <the proxy> so that loss terms which differentiate the proxy with respect to its inputs (Sobolev / derivative supervision) can use it; methods that do not need it ignore it. Fallback: supervised mean squared error between the completed prediction and the labels in targets (an L2ODataset restricted to the batch, or a Prediction). Self-supervised methods override it (see the penalty method in LearningToOptimize.jl).

source

train_proxy!(method, pipe::L2OPipeline, proxy, data; kwargs...)

Train proxy in place for method. L2OCore defines no method for it, since training depends on the ML framework; framework-specific packages (e.g. LearningToOptimize.jl for Flux) and method packages add methods.
